## 1. 问题现象与根本原因

### 1.1 现象

```
慢速（1m/s）：直角弯能转过去 ✓
快速（3m/s+）：直角弯转不出去，车子冲出去 ✗
```

车子感觉"慢半拍"——明明检测到拐点了，但车到路口时还没转过来。

### 1.2 三个叠加原因

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│  ① 电机响应延迟（硬件限制，无法消除）                  │
│     电机从 0 升到目标转速需要 50~100ms                 │
│                                                      │
│  ② 车身惯性（物理定律，只能补偿不能消除）               │
│     速度越快，刹车/转向时滑行距离越大                    │
│                                                      │
│  ③ 前瞻不够（软件问题，可以优化）                      │
│     只看到近处的拐点，来不及提前转弯                     │
│                                                      │
│  三者叠加 = 速度一快就转不过去                          │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 1.3 时间线分析

```
检测到拐点
  ↓ (0ms)
电机开始响应
  ↓ (50ms 延迟)     ← 电机还没转起来，车还在直走
电机达到目标转速
  ↓ (再 50ms)        ← 车身开始实际转向
  ↓
到达路口             ← 到这里时：要么还没转完，要么转过了
```

总延迟 ≈ 80~150ms。在这段时间内，车以当前速度直行：

| 车速 | 80ms 滑行距离 | 150ms 滑行距离 |
|------|-------------|---------------|
| 1 m/s | 8 cm | 15 cm |
| 2 m/s | 16 cm | 30 cm |
| 3 m/s | 24 cm | 45 cm |
| 4 m/s | 32 cm | 60 cm |

> 这就是"速度一快就转不过去"的物理原因——不是算法不行，是**物理上来不及**。

## 2. 电机响应延迟——硬件上必须存在的误差

### 2.1 电机不是开关

```
理想电机（不存在）：
  PWM 0 → PWM 8000：瞬间到达 → 无延迟

现实电机：
  时间     转速
  0ms  →   0 RPM
  10ms →   1000 RPM  （还在加速）
  20ms →   3000 RPM  （加速中）
  30ms →   5500 RPM  （接近目标）
  50ms →   7500 RPM  （基本到位）
  80ms →   8000 RPM  （稳定）
```

### 2.2 延迟的三个组成部分

```
总延迟 = 电气延迟 + 机械延迟 + 控制延迟

电气延迟：~1ms
  PWM 信号从 MCU 传输到驱动芯片

机械延迟：~30~80ms（主要部分）
  转子从静止加速到目标转速
  取决于：负载、目标速度、电机扭矩

控制延迟：~5ms
  PID 每 5ms 更新一次 PWM 输出

总计：约 40~90ms（低速）到 50~100ms（高速）
```

### 2.3 为什么速度越快延迟越大

```
低速时：
  电机负载小（摩擦力为主）
  加速快 → 延迟 ~30ms

高速时：
  电机负载大（空气阻力 + 摩擦力 + 车身惯性）
  加速慢 → 延迟 ~50~80ms
```

### 2.4 关键结论

> **电机响应延迟是硬件限制，代码无法消除。只能通过"提前发指令"来补偿。**

## 3. 前瞻距离与速度的数学关系

### 3.1 核心公式

```
所需前瞻距离 = 车速 × 总延迟时间

其中：
  车速 = 当前行驶速度（m/s）
  总延迟 = 电机响应时间 + 转弯执行时间（s）
```

### 3.2 不同速度下的前瞻需求

假设总延迟 = 80ms（电机响应 + 转弯执行）：

```
前瞻距离 = 车速 × 0.08

1 m/s → 8 cm    → 图像中约 row 40~50
2 m/s → 16 cm   → 图像中约 row 25~35
3 m/s → 24 cm   → 图像中约 row 15~25
4 m/s → 32 cm   → 图像中约 row 5~15
```

### 3.3 用生活类比

```
开车过路口：
  你看到路口 → 踩刹车 → 刹车需要 0.5s 才能停住
  如果时速 60km/h（16.7m/s）→ 刹车距离 = 8.3m
  如果时速 20km/h（5.6m/s）→ 刹车距离 = 2.8m

  速度越快，需要越早踩刹车。
  智能车同理：速度越快，需要越早发现拐点。
```

### 3.4 前瞻不够 vs 前瞻刚好 vs 前瞻太多

```
前瞻不够（end=40，3m/s）：
  发现拐点 → 8cm → 到达路口 → 电机还没响应完 → 冲出去 ✗

前瞻刚好（end=20，3m/s）：
  发现拐点 → 24cm → 电机响应完 → 车开始转 → 到路口时正好在转 ✓

前瞻太多（end=5，1m/s）：
  发现拐点 → 50cm → 电机响应完 → 车已经转完了 → 过早转弯 ✗
```

## 5. 摄像头角度的常见误区

### 5.1 误区："摄像头抬高 = 看得远"

```
❌ 错误理解：
  摄像头位置高 → 能看到更远的地方

✅ 实际情况：
  摄像头抬高 → 俯角变大（更朝下） → 看得更近
  
  因为摄像头位置高了，朝下看的角度更陡，
  同样的画面范围对应更近的地面区域。
```

### 5.2 正确理解

```
决定看得远不远的不是高度，是俯角：

俯角大（60°，朝下多）：
  ┌──────┐
  │ 📷\  │
  │    \60°
  │     \
  │      ● 近处路面
  └──────┘
  → 看得近，适合低速精确循迹

俯角小（30°，朝前多）：
  ┌──────┐
  │ 📷\  │
  │    \30°
  │     \
  │      \
  │       ● 远处路面
  └──────┘
  → 看得远，适合高速提前发现弯道
```

### 5.3 想看得远的正确方法

| 方法 | 效果 | 代价 |
|------|------|------|
| ~~抬高摄像头~~ | ✗ 反而看近了 | - |
| 减小俯角（往前倾） | ✓ 看得远 | 近处盲区变大 |
| **软件扩大搜索范围** | ✓ 看得远 | 远处可能误判（需配合去噪） |

> **推荐：不动摄像头，用软件扩大 `find_guaidian` 的搜索范围，配合八邻域去噪。**

## 6. 固定误差转弯法——4m/s 验证过的方法

### 6.1 你的代码做了什么

```
直角弯转弯流程：

1. find_guaidian() 找到拐点
2. corner_turn() / plan_turn() 决定转向方向
3. 进入 NODE_TURNING 状态
4. bias_left() / bias_right() 在拐点处画一条固定线
   → mid_line 被强制偏移
   → image_err 变成一个大的固定值
   → PID 输出最大转向
   → 电机一左一右打方向
5. yaw 角到达目标 → 回正 → 回到 NODE_NONE
```

### 6.2 类比

```
固定误差转弯 = 蒙眼开车到路口，听到"到了"就方向盘一把打死

不管路口是急弯还是缓弯，不管车速多少，
都是同一把方向、同一个力度。
```

### 6.3 这个方法能跑到 4m/s

四川队伍的实战验证：

```
固定误差转弯 + 八邻域去噪 + 四方位路径检测 = 4m/s 稳定过弯
```

**为什么简单方法反而有效？**

```
核心不在于转弯多平滑，而在于：
  1. 图像处理够稳 → 扫线不抖 → PID 跟得上
  2. 拐点检测够准 → 不误判 → 不会提前乱转
  3. 前瞻距离够远 → 来得及响应

只要这三个条件满足，固定误差转弯完全够用。
不需要搞平滑轨迹、不需要 S 形弯道规划。
```

### 6.4 为什么不需要复杂的转弯算法

```
复杂方法（轨迹规划）：
  优点：转弯平滑，过弯速度快
  缺点：代码复杂，调试困难，容易出 bug
  适用：工业级自动驾驶

简单方法（固定误差）：
  优点：代码简单，稳定可靠，容易调试
  缺点：转弯粗暴，有轻微过冲
  适用：智能车竞赛（速度有限，赛道简单）

竞赛场景下，简单 = 可靠 = 分数高。
```

## 7. 八邻域去噪——提速的核心前提

### 7.1 矛盾

```
想提速 → 需要看更远（前瞻拉大）
看更远 → 远处噪声多 → 拐点误判
误判 → 提前乱转弯 → 比不转还糟
```

### 7.2 解决方案

```
八邻域去噪 → 把远处的孤立噪声点去掉
  → 前瞻可以拉远而不误判
  → 速度就能上去

这就是 4m/s 队伍的核心秘密：
  不是转弯算法多牛，是图像处理够干净。
```

### 7.3 去噪与前瞻的配合效果

```
没有去噪，前瞻 row 40：
  误判率低 ✓    但速度上不去 ✗

没有去噪，前瞻 row 15：
  速度够了 ✓    但误判率爆炸 ✗

有去噪，前瞻 row 15：
  速度够了 ✓    误判率可接受 ✓   ← 目标状态
```

### 7.4 你的代码中去噪的位置

```c
// image_proc() 处理流程
image_scale(mt9v03x_image_1);     // 缩放
image_binarize(orig_image);        // 二值化
image_denoise();                   // ← 八邻域去噪（已加）
search_line();                     // 扫线
node_proc(bin_image);              // 节点检测（含 find_guaidian）
calc_image_error();                // 计算误差
```

去噪在二值化之后、扫线之前 → **所有后续处理（扫线、拐点检测）都受益于去噪**。

### 7.5 去噪强度的选择

```
same < 2：去噪太弱 → 远处噪声还在 → 误判多
same < 3：去噪适中 → 远处噪声基本去掉 → 白线边缘保留 ← 推荐
same < 4：去噪太强 → 白线边缘也被去掉 → 扫线丢失
```

## 8. 速度自适应前瞻方案

### 8.1 原理

```
前瞻距离 ∝ 车速

车速快 → 看更远（end 值减小）
车速慢 → 看更近（end 值增大）
```

### 8.2 速度与 end 值的对应关系

| 车速 | 所需前瞻 | 推荐 end 值 | 说明 |
|------|---------|------------|------|
| 1 m/s | 8 cm | 40 | 当前值，够用 |
| 1.5 m/s | 12 cm | 35 | 小幅调整 |
| 2 m/s | 16 cm | 30 | 中速 |
| 2.5 m/s | 20 cm | 25 | 中高速 |
| 3 m/s | 24 cm | 20 | 高速 |
| 3.5 m/s | 28 cm | 15 | 高速 |
| 4 m/s | 32 cm | 10 | 极速 |

### 8.3 实现思路（伪代码，不改代码）

```c
// 从编码器获取实际速度
float actual_speed = get_speed();  // m/s

// 根据速度计算前瞻范围
uint8 guaidian_end;
if (actual_speed < 1.5f)       guaidian_end = 40;
else if (actual_speed < 2.0f)  guaidian_end = 35;
else if (actual_speed < 2.5f)  guaidian_end = 30;
else if (actual_speed < 3.0f)  guaidian_end = 25;
else if (actual_speed < 3.5f)  guaidian_end = 20;
else                           guaidian_end = 10;

find_guaidian(ROW - 5, guaidian_end);
```

### 8.4 前提条件

要做速度自适应，需要先有：

1. **编码器读取实际速度**（硬件已有，代码未实现速度计算）
2. **速度闭环控制**（当前是开环，`base_speed` 直接输出 PWM）

### 8.5 当前阶段不建议做

```
原因：
  1. 开环控制下，实际速度不等于设定速度
  2. 编码器→速度的换算需要标定（轮子直径、编码器线数）
  3. 增加了调试复杂度

建议：
  先用固定前瞻 + 手动调到最佳值
  等上了速度闭环再做自适应
```

## 9. 实战调参流程

### 9.1 第一步：确定当前最佳前瞻值

```
固定 base_speed 不变
只改 find_guaidian 的 end 值

从 end=40 开始，每次减小 5：
  40 → 35 → 30 → 25 → 20 → 15 → 10

记录每个值的表现：
  - 直角弯能不能转过去？
  - 有没有提前误转？
  - 有没有过冲？

找到"刚好能转过去"的最小 end 值 = 你的最佳前瞻

### 9.2 第二步：提速后重新调

```
加大 base_speed
重复第一步

你会发现：速度越快，最佳 end 值越小（需要看得更远）

## 10. 从 1m/s 到 4m/s 的完整路径

### 10.1 阶段一：1~2m/s（当前水平）

```
目标：稳定跑完一圈，不丢线，不误判

核心工作：
  □ 八邻域去噪（已加）
  □ 固定前瞻 end=40（当前值）
  □ 固定误差转弯（当前方法）
  □ 基础 PID 调好
  □ 启动脉冲调好（已加）

关键指标：
  ✓ 直角弯能转过去
  ✓ 不丢线
  ✓ 不误判
```

### 10.2 阶段二：2~3m/s

```
目标：提速后弯道还能过

核心工作：
  □ 前瞻拉远 end=25~30
  □ 去噪强度确认够用
  □ PID 参数重新微调（速度变了 PID 要跟）
  □ 启动脉冲微调

关键指标：
  ✓ 直角弯能转过去
  ✓ 无明显过冲
  ✓ 无误判
```

### 10.3 阶段三：3~4m/s

```
目标：接近竞赛水平

核心工作：
  □ 前瞻拉到 end=10~20
  □ 八邻域去噪 + 四方位路径检测
  □ 考虑速度闭环（编码器反馈）
  □ 考虑速度自适应前瞻

关键指标：
  ✓ 直角弯稳定通过
  ✓ 速度损失最小
  ✓ 零误判
```

### 10.4 阶段四：4m/s+

```
目标：竞赛级水平

核心工作：
  □ 全部优化到位
  □ 硬件调优（电机、轮子、赛道材质）
  □ 电磁传感器融合（如果有的话）
  □ 极限参数压榨

关键指标：
  ✓ 全赛道稳定
  ✓ 零失误
  ✓ 时间最短
```

### 10.5 每个阶段的核心公式

```
1~2m/s：  图像处理 > 转弯算法
          先把扫线做稳，再去想怎么转

2~3m/s：  前瞻匹配 > PID 调参
          前瞻距离对了，PID 自然好调

3~4m/s：  去噪质量 > 前瞻距离
          去噪做好了，前瞻才能拉远

4m/s+：   硬件 > 软件
          软件已经到极限了，靠硬件提升
```

| 速度越快越转不过去 | 所需前瞻随速度增大 | 速度自适应前瞻（后续做） |
| 转弯过冲/甩尾 | 固定误差太猛 | 当前可接受，后续优化 |
| 摄像头抬高反而看近了 | 俯角变大 | 往前倾（减小俯角） |
| 电机启动卡住 | 静摩擦力大 | 启动脉冲（已加） |

## 附录 B：核心结论

> **图像处理 > 转弯算法。去噪做好了，简单方法也能跑 4m/s。**

> **速度每翻一倍，前瞻距离也要翻一倍。这是物理定律，代码只能补偿不能违背。**

> **先跑通再优化。不要一上来就搞自适应、搞轨迹规划。固定前瞻 + 手动调参，先跑到 2m/s。**
