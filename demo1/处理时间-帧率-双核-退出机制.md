# 疯狂电路 — 处理时间、帧率、单核双核、264与副本退出机制

---

## 一、双核能提升什么？

### 不能提升的东西

| 项目 | 原因 |
|------|------|
| ❌ 单帧处理时间 | 算法决定的，换核没用 |
| ❌ 摄像头帧率 | 硬件决定的 |

### 能提升的东西

| 项目 | 说明 |
|------|------|
| ✅ 并行处理 | CPU0 和 CPU1 同时干活，互不阻塞 |
| ✅ 响应速度 | 电机控制、蓝牙通信不用等摄像头处理完 |

### 当前 vs 双核

```
【当前单核】CPU0 串行执行：
┌──────────────┬──────────┬──────────┐
│ 摄像头处理    │ 电机PID   │ 蓝牙通信  │
│ 0.5ms        │ 0.1ms    │ 0.1ms    │
└──────────────┴──────────┴──────────┘
总时间: 0.7ms（一个接一个）

【双核并行】CPU0 + CPU1 同时：
CPU0: ┌──────────┬──────────┐
      │ 电机PID   │ 蓝牙通信  │
CPU1: ┌──────────────┐
      │ 摄像头处理    │
      └──────────────┘
总时间: ~0.5ms（两个核同时跑，取最长的那个）
```

> 📌 **实际意义**：电机控制更及时，不会因为摄像头处理占用 CPU 而出现控制延迟。对高速行驶时的稳定性有帮助。

## 二、单帧处理时间缩短 → 省出 CPU 时间

| 省出来的时间可以干嘛 | 效果 |
|---------------------|------|
| 跑更复杂的算法 | 比如副本的多行拐点检测、环岛识别 |
| 电机 PID 跑更高频率 | 控制更平滑，车更稳 |
| 加更多功能 | 蓝牙调参、OLED 显示、多传感器融合 |

---

## 三、摄像头帧率提高 → 看得更频繁

| 帧率 | 含义 | 效果 |
|------|------|------|
| 30fps | 每 33ms 看一次 | 车速快时可能漏掉弯道 |
| 50fps | 每 20ms 看一次 | 常规够用 |
| 100fps | 每 10ms 看一次 | 高速时也能及时反应 |

### 两个一起提升 → 车能跑更快更稳

```
帧率低 + 处理慢 = 蒙着眼跑步，每隔很久才睁眼看一次路
                   → 跑慢了还行，跑快了就撞墙

帧率高 + 处理快 = 眼睛一直盯着路，反应极快
                   → 高速过弯也不会冲出去
```

> 🎯 **对你来说最实际的收益**：车速可以提上去，过弯不容易冲出赛道。

## 四、三者关系一图看懂

```
摄像头帧率 = 每隔多久给你一张新图（硬件决定）
处理时间   = 你算完一张图要多久（算法决定）
双核       = 能不能一边算图一边干别的（架构决定）
```

### 用时间轴来看

场景：50fps 摄像头，处理一帧 500μs

```
时间轴（每格 = 1ms）：

摄像头: |新图|      |新图|      |新图|      |新图|
        0ms        20ms       40ms       60ms
        └── 20ms一帧 ──┘

【单核】CPU0 串行：
CPU0: [算图0.5ms][空闲19.5ms][算图0.5ms][空闲19.5ms]
        ↑                    ↑
        处理完才轮到别的活

【双核并行】CPU0 + CPU1：
CPU1: [算图0.5ms][空闲19.5ms][算图0.5ms][空闲19.5ms]
CPU0: [电机PID][蓝牙][电机PID][蓝牙]...  ← 全程不被阻塞
```

### 三种组合的实际效果

| 帧率 | 处理时间 | 单核/双核 | 车的表现 |
|------|----------|-----------|----------|
| 30fps (33ms) | 500μs | 单核 | ⚠️ 33ms 才看一次，高速过弯来不及反应 |
| 30fps (33ms) | 500μs | 双核 | ⚠️ 看得慢，但电机控制不受影响 |
| 50fps (20ms) | 500μs | 单核 | ✅ 够用，但电机 PID 要等算图 |
| 50fps (20ms) | 500μs | 双核 | ✅✅ 看得及时，控制也流畅 |
| 100fps (10ms) | 500μs | 双核 | 🏆 最佳，高速也能实时反应 |

### 一句话总结

> **帧率决定"多久看一次路"，处理时间决定"看完要算多久"，双核决定"算图时电机能不能同时跑"。三个一起好，车才能又快又稳。**

## 五、36000 是怎么来的

```
36000 = 编码器分辨率 × 减速比 / 车轮周长
```

### 编码器分辨率

查电机/编码器的数据手册，找类似 **PPR**（Pulses Per Revolution）或 **CPR** 的参数。

比如电机标称"500 线编码器"，就是转一圈产生 500 个脉冲。

### 减速比

查电机数据手册，找 **Gear Ratio**。

比如电机标称"减速比 1:30"，就是电机内部马达转 30 圈，输出轴转 1 圈。

### 车轮周长

自己量：

```
车轮周长 = π × 车轮直径
```

拿尺子量车轮直径，乘以 3.14。

比如直径 65mm → 周长 = 3.14 × 65 = 204mm = 0.204m

### 但最靠谱的方法：实测标定

```
公式: ONE_METER = 编码器分辨率 × 减速比 / 车轮周长(m)
```

**实测步骤：**

1. 在地上量出 1 米，标记起点和终点
2. 把车从起点推到终点
3. 同时记录编码器脉冲总数

```
ONE_METER = 1米内累计的脉冲数
```

> 📌 这样就不需要查手册，直接测出来最准。

## 六、264 与副本退出机制对比

### 副本的退出方法（角度验证 + 编码器距离）

副本的路口处理是**状态机 + 角度验证**，不是单纯的距离阈值。

**以十字直行为例：**

```c
// 副本 Elment_Handle_Cross() — 直行退出
if(ImageFlag.image_element_cross_flag == 3      // 状态机：已进入处理阶段
   && Path[...].memory_target_angle_turn[...] == 'N'  // 预设直行
   && encoder.disA >= encoder.target_distance)  // 编码器距离够了
{
    buzzer_off();
    encoder_clear();                // ← 清零编码器，关键！
    ImageStatus.Road_type = Normol; // ← 退出
    Path[...].target_angle_index++; // ← 切换到下一个路径点
}
```

**左转/右转的退出：**

```c
if(abs(post.diff_angle) < 10 && ImageFlag.image_element_cross_flag == 3)
{
    encoder_clear();    // ← 清零编码器
    ...
}
```

### 核心差异对比

| 维度 | 264（你现在的） | 副本 |
|------|---------------|------|
| **退出判据** | 固定距离 0.25m + 路径数 < 3 | 陀螺角度到位 或 编码器到达目标距离 |
| **距离管理** | `total_dist` 单调递增，不清零 | `encoder_clear()` 每次退出清零 |
| **路径切换** | 无路径表，手动处理 | `Path[path].target_angle_index++` 自动切换 |
| **状态机** | 简单（DETECTED → TURNING） | 完整（1→2→3，识别→处理→验证） |

### 264 的问题在哪

你的 `total_dist - start_dist > 0.25f` 有两个隐患：

1. **距离是固定的**，不根据实际路况调整。低速时等太久，高速时可能不够
2. **退出后 `total_dist` 不清零**，累计值越来越大，后续路口的距离判断会受影响

### 更好的退出方法

借鉴副本的思路，结合你 264 现有的代码结构，建议改成**编码器距离 + 路径数双重验证**：

```c
// ======================== 改进后的退出逻辑 ========================
case NODE_TURNING:
    find_guaidian(ROW - 5, 30);

    if (turn_dir == GO_STRAIGHT)
    {
        static float start_dist = 0.0f;
        static uint8 started = 0;

        if (!started)
        {
            start_dist = total_dist;
            started = 1;
        }

        // 改进：距离到了就直接退出，不再等路径数 < 3
        // 因为距离够了 = 车已经离开路口了
        if (total_dist - start_dist > 0.25f)
        {
            // 记录退出时的偏航角
            yaw_after_turn = yaw_total;
            float delta_yaw = yaw_after_turn - yaw_before_turn;
            if (delta_yaw < -30.0f)
                actual_turn_dir = TURN_LEFT;
            else if (delta_yaw > 30.0f)
                actual_turn_dir = TURN_RIGHT;
            else
                actual_turn_dir = GO_STRAIGHT;

            if (actual_turn_dir == turn_dir)
                turn_verify_flag = 1;
            else
                turn_verify_flag = 2;

            node_reset_state(&yaw_locked, &cur_paths);
            started = 0;
            // ======================== 关键：清零累计距离 ========================
            total_dist = 0.0f;
        }
    }
```

**改动点：**

1. 去掉 `find_rect_path(bin_image) < 3` 的二次检查 — 路口内路径数波动大，这个条件反而导致退出不稳定
2. 距离到了就退出，简单可靠
3. 退出后清零 `total_dist`，避免累计误差

## 七、副本为什么更好

| 维度 | 264 | 副本 | 胜 |
|------|-----|------|-----|
| **退出判据** | 固定距离，不看实际姿态 | 角度到位才退 | **副本** |
| **距离管理** | 相对快照，不清零 ✅ | 清零，累计会漂 | **264** |
| **路径切换** | 手动，易出错 | 表驱动，可扩展 | **副本** |
| **状态机** | 2 态 | 3 态，更严谨 | **副本** |

### 副本的核心优势在退出判据

```
264：  走了 0.25m → 退出（不管车转没转完）
副本：  陀螺检测到角度到位 → 退出（确认动作完成）
```

- `0.25m` 是"我觉得该走了"
- 角度验证是"确认我真的转完了"

后者在低速/高速/打滑等场景下都更可靠。

### 264 唯一的优势是距离管理

`total_dist` 用相对快照不清零，多路口不会累计漂移。副本的 `encoder_clear()` 每次清零，单次没问题，但频繁操作可能有微小累积误差。

> 🎯 **建议**：取副本的退出判据 + 保留 264 的距离管理方式。

## 八、实际的读取时序

以你的 264（改双核后）为例：

```
中断（CPU0）                    图像处理（CPU1）
  │                               │
  ├─ 1ms: control_proc()          │
  ├─ 5ms: gyro_proc()  ──写──→ yaw_total（陀螺累计角度）
  ├─ 5ms: encoder_proc() ──写──→ total_dist（编码器累计距离）
  │                               │
  │                        摄像头帧就绪 → image_proc() 被触发
  │                               │
  │                        读取 yaw_total, total_dist
  │                        做退出判断
```

> 📌 陀螺和编码器是**中断里实时累加**的，不是每隔几秒读一次。图像处理触发时，读到的是截至那一瞬间的最新累计值。

### 时间错位会不会有问题？

**会有，但影响很小：**

```
假设车速 1m/s，摄像头 50fps，图像处理耗时 5ms

时刻 0ms：  image_proc() 读到 total_dist = 0.23m → 不退出
时刻 5ms：  image_proc() 读到 total_dist = 0.28m → 退出
这 5ms 内车只走了 5mm，不影响判断
```

### 真正可能出问题的场景

| 场景 | 风险 | 严重程度 |
|------|------|----------|
| 图像处理耗时太长（>50ms） | 读到的值已经过时很多 | 中 |
| 陀螺漂移 | `yaw_total` 累计误差变大 | 低（短时间不大） |
| 两核同时读写同一个变量 | 读到半更新的值 | 极低（32 位读写原子） |

### 结论

**不需要额外同步机制。** 原因：

1. 中断每 5ms 更新一次累计值，图像处理每 10-20ms 读一次 — 误差最多 5ms 内的距离/角度变化，对路口判断影响可忽略
2. `total_dist`、`yaw_total` 都是 float（32 位），TC264 上单次读写是原子的，不会读到"一半旧一半新"的值
3. 智能车速度一般 1-2m/s，5ms 内最多移动 10mm，不会导致误判

> 副本的方案也是一样的时序，不存在比这更精确的方法，除非用硬件触发同步（成本太高，没必要）。

## 九、`total_dist` 用相对快照不清零 — 大白话解释

看你的代码就明白了：

```c
// image.c — 进入直行路口时
case NODE_TURNING:
    if (turn_dir == GO_STRAIGHT)
    {
        static float start_dist = 0.0f;
        static uint8 started = 0;

        if (!started)
        {
            start_dist = total_dist;   // ← 这就是"快照"：记下此刻的累计值
            started = 1;
        }

        if (total_dist - start_dist > 0.25f)  // ← 用差值判断，不关心 total_dist 本身多大
        {
            // 退出路口
        }
    }
```

**用大白话说：**

```
total_dist 一直在涨（编码器每5ms累加）：
  启动时：  total_dist = 0
  第1个路口：total_dist = 1.5m
  第2个路口：total_dist = 3.2m
  第3个路口：total_dist = 5.8m  ← 越来越大，从不清零

进入第3个路口时：
  start_dist = 5.8m（快照）
  
车又走了 0.25m 后：
  total_dist = 6.05m
  6.05 - 5.8 = 0.25m → 退出
```

> 📌 **"不清零"的意思就是**：`total_dist` 从启动开始一路累加，不会在路口退出时归零。每次进路口只记一个"起点快照"，用差值判断走了多远。

**这和副本的 `encoder_clear()` 不同** — 副本每次退出路口就把编码器清零，下次从 0 开始算。
